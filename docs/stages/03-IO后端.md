## 二、为什么这么做（Why）

**动机**：阶段 1 的循环只会等一个 `Waker` event，接不了真实 I/O。阶段 3 把等待环节换成 IOCP，并正面回答大纲里点名的「最难也最值钱的部分」——**异步对象的生命周期**：回调里删 watcher、关句柄、重入分发，怎么才能不 use-after-free。

**对应约束编号：**
- `C1` 主后端 IOCP + 同一套接口可切后端 → `IWaitBackend` + `IocpBackend`；`WakerBackend` 保默认，阶段 5 的 WFMO 后端只需再实现一遍接口。
- `C2` Overlapped 带独立上下文 → `IoContext` 内嵌 `OVERLAPPED`，由 `lpOverlapped` 反查；`generation` 丢弃过期包。
- `C3` `uv_close` 式状态机 → `Watcher` 三态 + `inflight_` 计数。
- `C4` `CancelIoEx → 排空 → join → 释放` → `Close()` 只 `CancelIoEx`；`Reap()` 只在 `kClosed` 后 delete。
- `C7` overlapped 打开并关联 IOCP → `DirWatcher` 用 `FILE_FLAG_OVERLAPPED`，构造时 `Associate()`。
- `B1`/`B2` → `Wait()` 只取包不跑回调，`Dispatch()` 在 loop 线程跑回调；`TimerHeap`/`Renderer` 仍无锁。
- `A1`/`A4` → 零第三方依赖，测试框架自建。
- `F4` → `01-约束.md` 增加「C1 落地补充」段落（细化而非偏离）。
- `F5` → 13 个测试 + 真实目录端到端 + demo。

**被放弃的方案及原因：**

| 放弃 | 原因 |
|---|---|
| 直接把 `Waker` 换成 IOCP、删掉 event | 会让阶段 1/2 全部测试失效；抽象成 `IWaitBackend` 后默认后端不变，零回归，且自然满足 C1「同一套接口切换后端」 |
| 在 `Wait()` 里直接执行 completion 回调 | 违反 B2（回调必须在 loop 线程、且要能安全 PostTask/关 watcher）；拆成 `Wait`(取包) + `Dispatch`(跑回调) |
| `Close()` 里直接 `delete this` / `delete ctx` | 已提交给内核的 overlapped 操作还会产生 completion，写进已释放内存 → use-after-free。改为 `CancelIoEx` + `inflight_` 归零后由 `EventSource::Reap()` 延迟回收 |
| 用 `std::priority_queue` / 线程池定时轮询目录 | 违背「I/O 通知」学习目标；`ReadDirectoryChangesW` 是纯内核通知、overlapped 语义清晰、无需硬件 |
| `ReadDirectoryChangesW` 用同步 `lpBytesReturned` 阻塞等 | 违反 C7/事件驱动；用 overlapped + IOCP |
| 靠 `OVERLAPPED.hEvent` 事件 | 与 IOCP 模型不一致；本项目统一走 `PostQueuedCompletionStatus` / completion port |

**这个决定让哪件事变得可见：**
1. **为什么 Windows 需要 IOCP**：一个 completion port 就能同时等「目录变更 / 定时器窗口 / 跨线程 postTask」，且没有 `WaitForMultipleObjects` 的 64 句柄上限。阶段 5 写 WFMO 后端时会亲手撞上这个上限。
2. **异步对象的生命周期到底难在哪**：不是「怎么发起 I/O」，而是「关闭时还有几个 completion 在路上」。`inflight_` + generation + 延迟回收把这件事变成可验证的状态机。
3. **「回调里关闭自己」是安全的**：因为 `Close()` 不释放内存，只标记 + 取消；真正 delete 推迟到 `Reap()`，且在 loop 线程。

## 三、怎么做的（How）

### 3.1 关键数据结构

**`IoContext`**（约束 C2）
```cpp
struct IoContext {
    OVERLAPPED ov{};            // 第一个成员：由 lpOverlapped 反查
    std::vector<uint8_t> buffer;
    IoCallback callback;        // void(uint32_t bytes, uint32_t error)
    uint64_t generation;        // 丢弃过期完成包
    void* owner;                // 所属 Watcher
    uint32_t error;
    bool cancelled;             // 测试注入 / CancelIoEx 取消包标记
};
```

**`Watcher` 状态机**（约束 C3）
```
kActive ──Close()──► kClosing ──inflight_归零──► kClosed ──Reap()──► delete
   │                     ▲                          ▲
   └─ 正常 completion ───┴── Notify → 回调内可再次 Close()
        → 重新 Arm（generation++）
```
- `inflight_`：已提交未完成的 overlapped 操作数。`BeginOperation` 增，`OnCompletion` 减。
- `Close()`：`CancelIoEx(handle, nullptr)` → 每个被取消的操作仍会产一个 completion，因此**绝不能在这里释放内存**。
- 快路径：若 `Close()` 时 `inflight_==0`（例如回调内部关闭，本次 completion 已被消费），直接 `kClosed`。

**`IocpBackend::Entry`**：`Wait()` 把 `OVERLAPPED_ENTRY` 转成 `Entry` 存入 `pending_`；`Dispatch()` 逐个 `DrainOne`，按 `lpCompletionKey` 区分 `kKeyWake` / `kKeyWatcher` / `kKeyTask`。

### 3.2 核心流程 / 调用链

```
[EventLoop::RunIteration]
  backend_->Dispatch()         ← 上一轮 Wait 收集的完成包，回调在 loop 线程
  DispatchPostedTasks()
  DispatchDueTimers()
  DispatchIdle()
  backend_->Wait(timeout)      ← GetQueuedCompletionStatusEx 批量取包，不跑回调

[Wake] PostQueuedCompletionStatus(iocp, 0, kKeyWake, nullptr)  ← Windows self-pipe

[目录事件真实链路]
  ReadDirectoryChangesW(handle, buf, ..., &ctx.ov)  → ERROR_IO_PENDING
         │ 文件被创建
         ▼
  内核投递 completion → GQCSEx 取到 Entry(key=kKeyWatcher, ov=&ctx.ov)
         ▼
  Dispatch → ContextFromOverlapped(ov) → ctx.callback(bytes, error)
         ▼
  Watcher::OnCompletion → Notify() → Parse(FILE_NOTIFY_INFORMATION) → DirCallback
         ▼  （若未关闭）
  重新 Arm：generation++ / ResetForReuse / ReadDirectoryChangesW

[优雅关闭，约束 C4]
  source.CloseAll()  → 每个 Watcher::Close() → CancelIoEx → kClosing
  内核投递取消包(ERROR_OPERATION_ABORTED) → Dispatch → OnCompletion → inflight-- → kClosed
  source.Reap()      → 只删 kClosed 的 watcher（CloseHandle 在状态机内完成）
  loop.Stop()        → Run() 退出前 Dispatch + Shutdown(排空/关 IOCP 句柄)
```

### 3.3 用到的 Win32 API

| API | 用途 |
|---|---|
| `CreateIoCompletionPort` | 建端口（NumberOfConcurrentThreads=1）+ `Associate` 关联目录句柄（C7） |
| `GetQueuedCompletionStatusEx` | 批量取完成包（一次最多 64 条），支持 timeout |
| `PostQueuedCompletionStatus` | 唤醒 loop（`kKeyWake`）/ 测试可控注入完成包 |
| `CreateFileW(FILE_FLAG_BACKUP_SEMANTICS \| FILE_FLAG_OVERLAPPED)` | 目录句柄（overlapped + 允许打开目录） |
| `ReadDirectoryChangesW` | 提交 overlapped 目录变更监听 |
| `FILE_NOTIFY_INFORMATION` / `NextEntryOffset` | 解析变更记录链表 |
| `CancelIoEx` | 取消句柄上所有挂起 overlapped 操作（C4 第一步） |
| `CloseHandle` | 关目录句柄 / 关 IOCP 端口 |

### 3.4 遇到的坑与处理（真实发生）

| 坑 | 现象 | 处理 |
|---|---|---|
| **回调里 `Close()` 后仍重新 Arm** | 初版 `OnCompletion` 在 `Notify()` 后无条件 `BeginOperation`，导致回调请求关闭后又提交了新操作 | 加 `if (state_ == kActive && !close_requested_)` 守卫；关闭后 fall through 到收尾分支 |
| **`Close()` 内直接 delete 会 use-after-free** | 设计推演：取消的操作仍会产 completion | `Close()` 不释放；`EventSource::Reap()` 只在 `kClosed` 后 delete，且回收在 loop 线程 |
| **测试期望写错（kClosing vs kClosed）** | `close_from_inside_callback_is_safe` 断言 `kClosing/inflight=1` 实际得到 `kClosed/inflight=0` | 这其实是**正确的快路径**：进入 OnCompletion 时 inflight 已减到 0，无挂起操作可直接关闭。修正测试断言并加「generation 未递增」检查 |
| **`CHECK_EQ(wstring)` 编译失败** | 窄 `ostringstream` 不接受 `std::wstring` → `error C2679` | `test_framework.h` 的 `Str()` 增加 `std::wstring` / `wchar_t` 分支 |
| **`ClosingWatcher` 缺访问器** | 局部测试类没暴露 `inflight()` → `error C2039` | 加 `inflight()` / `gen()` 访问器 |
| **`lpBytesReturned=nullptr` 有争议** | overlapped 下 MSDN 允许但实现依赖版本 | 改用成员 `DWORD bytes_returned_`，避免悬空指针与歧义 |
| **取消包的 error 传递** | `GQCSEx` 不直接给 GetLastError 风格错误码 | `IoContext` 增加 `error`/`cancelled`；`DrainOne` 把 `STATUS_CANCELLED` 或 `cancelled` 统一转成 `ERROR_OPERATION_ABORTED` 传给状态机 |
| **测试注入 completion 与真实 completion 混用** | 需要不依赖内核精确驱动状态机 | `FakeWatcher` 用 `PostCompletion(kKeyWatcher, ..., &ctx.ov)` 可控注入；同时保留一个**真实目录端到端**测试兜底 |
| **EventLoop 退出时 Shutdown 关掉 IOCP** | 测试想在 `Run()` 后手动排空会失败 | 把 `CloseAll → 取消包 → Reap → Stop` 全部放进 loop 内的定时器里完成，符合真实关闭时序 |

### 3.5 线程 / 生命周期时序

```
主线程(loop)          内核/I/O          测试/创建线程
  │ IocpBackend 构造（CreateIoCompletionPort）
  │ DirSource::Start → ReadDirectoryChangesW 提交 ctx.ov
  │ EventLoop::Run
  │   Wait(timeout) ─────────────────────────► 阻塞在 completion port
  │                    文件创建 ───────────────► 投递 completion
  │   ◄─────────────── GQCSEx 取到 Entry
  │   Dispatch → ctx.callback → OnCompletion → Notify → DirCallback → 渲染标脏
  │   （未关闭）重新 Arm → ReadDirectoryChangesW
  │   ...
  │   [t=600ms 定时器] CloseAll → CancelIoEx → kClosing
  │   ◄─────────────── 取消包(ERROR_OPERATION_ABORTED)
  │   Dispatch → OnCompletion → inflight=0 → kClosed → CloseHandle
  │   [t=900ms 定时器] Reap → delete watcher；loop.Stop()
  │   Run() 退出：Dispatch + Shutdown(排空 + 关 IOCP)
  ▼ 返回，watchers_left=0，state=kStopped
```

全过程 `WakerBackend`（默认）与 `IocpBackend`（注入）共用同一个 `EventLoop`；`Renderer` 仍在 loop 线程，无锁。

## 六、遗留 / 下一阶段衔接

**遗留：**
- `IocpBackend::DrainOne` 目前只把 `STATUS_CANCELLED` / `ctx.cancelled` 转成 `ERROR_OPERATION_ABORTED`；其它 Win32 错误（句柄失效、缓冲溢出 `ERROR_NOTIFY_ENUM_DIR`）尚未细分处理，阶段 4 加 socket/管道时再补错误分类。
- `Watcher` 目前**一个 watcher 一个固定 `IoContext`**（一次一个挂起操作）。阶段 4 做全双工 socket 需要「读/写各一个 context」，应把 `IoContext` 改成由对象池管理多个 context，`inflight_` 计数天然支持。
- `DirWatcher` 用 `bWatchSubtree=FALSE`、4096 字节缓冲；大量短时变更可能溢出，后续可加 `ERROR_NOTIFY_ENUM_DIR` 重扫逻辑。
- 阶段 5 的 `WaitForMultipleObjectsEx` 后端已由 `IWaitBackend` 预留位置，尚未实现；届时才会亲手撞上 64 句柄上限。
- worker 线程池（约束 B3）尚未登场；阶段 4 用 `kKeyTask` 完成包把解析结果回投 loop。
- `/showIncludes` 编译噪音来自本机 MSVC/CMake 环境，未查明根因，不影响构建。

**下一阶段（阶段 4：更多 source + 线程池）需要本阶段提供的接口：**
- `IocpBackend::Associate` / `PostCompletion(kKeyTask)` —— 子进程管道、TCP/UDP 关联到同一端口；worker 回投任务。
- `Watcher` / `EventSource::CloseAll` / `Reap` —— 每个新 source 直接派生，复用 close 状态机。
- `EventLoop(IClock&, unique_ptr<IWaitBackend>)` —— 注入 IOCP 后端，路径已验证。
- `Renderer::RenderTick` / `KeyViewer` —— 新 source 的数据画进同一画面。

**需要提前注意的坑：**
- 全双工 socket 必须给「读」和「写」各一个 `IoContext`，否则两个 overlapped 操作共用一个 `OVERLAPPED` 会互相覆盖。
- worker 线程池只做无状态计算（约束 B3），结果经 `PostCompletion(kKeyTask)` 回投，**不得**直接调 `Renderer::Put` 或碰 `Watcher` 状态。
- 子进程管道那一路要用 `CreateProcess` + 匿名管道 overlapped 读 + 进程句柄等待，别用同步 `ReadFile`。
- 关闭顺序仍是 `CloseAll → 取消包 → Reap → Stop`，别在 `Reap` 之前 `delete`。
