## 二、为什么这么做（Why）

- **动机**：用户明确要求「先写一个大纲和约束文档」「每个阶段留下文档（做了什么/为什么/怎么做）」「执行前先用 git 并在 GitHub 建仓库」。阶段 0 就是把这三件事本身作为第一个可交付物。
- **对应约束编号**：F1（每阶段必须留文档）、F2（统一放 `docs/stages/`）、F3（阶段级 commit）、F6（不写凭据/绝对路径）。
- **被放弃的方案**：
  - 放弃「第一版直接做串口网络助手」：硬件依赖 + 协议/hex 编辑代码量会盖过 runtime 本身，且一次性把串口/socket/overlapped/IOCP 全压上来难以定位问题（详见 `00-大纲.md` 1.2）。
  - 放弃「VT/ANSI 作为主渲染路径」：会绕过双缓冲差分渲染这一最有学习价值的部分（约束 D1/D3）。
  - 放弃「定时器用 `CreateTimerQueueTimer`」：回调跑在线程池线程上，破坏单线程分发（约束 C5）。
  - 放弃「引入 libuv / asio 等参考实现」：学习目标就是自己实现事件循环（约束 A1）。
- **这个决定让什么变得可见**：把「文档即契约」前置，使得后续每个阶段的偏离都必须显式登记（约束 F4），避免边写边改、最后说不清为什么这么设计。

### 3.2 核心流程 / 调用链
1. 探查：`git --version`、目录为空、无 `gh` CLI、`git config` 无 user 信息。
2. 认证：Windows 凭据管理器存在 `git:https://day-day-upup@github.com`，经 `git credential fill` 读取（不打印密钥）；GitHub API `GET /user` 验证为 `day-day-upup`，token 含 `repo` scope。
3. 建仓：`POST /user/repos`，参数 `{name, description, private:false, license_template:MIT, auto_init:false}`。
4. 本地：`git init -b main` → 仓库级 config → `git remote add origin`。

### 3.3 用到的 Win32 / 系统接口
- Windows Credential Manager（经 Git Credential Manager）、`cmdkey /list` 检查凭据存在性。
- GitHub REST API（`curl.exe`，Schannel）。
- git 仓库级配置（`git config --local`）。

### 3.4 遇到的坑与处理（本阶段真实发生，值得记录）

| 坑 | 现象 | 处理 |
|---|---|---|
| JSON 请求体带 BOM | `[System.IO.File]::WriteAllText` 默认 UTF8Encoding 写出 `EF BB BF`，`POST /user/repos` 返回 `400 Problems parsing JSON` | 改用 `New-Object System.Text.UTF8Encoding($false)`，并给 `--data-binary @file` 用正斜杠路径；重试得 `201 Created` |
| Schannel 证书吊销检查超时 | `Invoke-RestMethod` / `curl.exe` 直连报「基础连接已经关闭 / exit 35」，加 `--ssl-no-revoke` 后 API 正常 | 这是本机网络对吊销检查站点不可达导致的，与 GitHub 认证无关 |
| `github.com:443` 不可达 | DNS 只解析到 `20.205.243.166`，该 IP 443 连接 21s 超时；`api.github.com`（`.168`）可达；git 内置 libcurl 严格按 DNS 解析故 push 失败 | 扫描到 `140.82.116.3` 可承载 github.com HTTPS，通过 `http.curloptResolve` 配置；该 IP 间歇性可用。此项记为**环境事实**，写进 `01-约束.md` G 节，不写死到项目代码 |
| 本地代理 `127.0.0.1:7897` 不可用 | 系统开了该代理，但 HTTPS CONNECT 到 GitHub 失败（exit 28/35） | 不依赖它，走直连 + 可达入口 |
| GCM 在非交互环境行为不稳定 | 带 token 的 URL + `curloptResolve` 可 `ls-remote` 成功；走 GCM 注入凭据时出现 `Recv failure: Connection was reset` | 推送采用「临时 token URL 覆盖 + 显式 `-c` 网络参数」，token 只在命令期存在；若仍失败，兜底用 GitHub REST API 直接提交文件 |

> 结论：认证链路有效、仓库已建；网络层需要按 G 节的环境约束处理。这些是本机环境问题，不影响项目设计。
