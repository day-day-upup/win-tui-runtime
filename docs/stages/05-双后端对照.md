## 二、为什么这么做（Why）

**动机**：阶段 3 用 IOCP 时「为什么 Windows 需要 IOCP」还只是文档里的一句话。阶段 5 的目的就是**亲手把另一个后端写一遍，撞上它的限制**，让这句话变成体感。对应大纲学习目标 2（掌握 Windows 异步 I/O 模型）与约束 C1。

**对应约束编号：**
- `C1` 主后端 IOCP + 阶段 5 WFMO 对照 → `IWaitBackend` 已有抽象，注入 `WfmoBackend` 即切换，`EventLoop::RunIteration` 一行未改。
- `B2` 回调只在 loop 线程 → `WfmoBackend::Wait()` 只记录「哪个 slot 被 signaled」/ APC 入队，`Dispatch()` 才在 loop 线程跑回调。
- `B5` 跨线程唤醒 → slot 0 复用阶段 1 的 `Waker`（auto-reset event），`Wake()` = `SetEvent`。
- `F5` → 11 个测试 + demo。
- `A1` → 零第三方依赖，全部 Win32 原生 API。

**被放弃的方案及原因：**

| 放弃 | 原因 |
|---|---|
| 改 `EventLoop::RunIteration` 来适配 WFMO | 违反 C1「同一套接口切换后端」；`IWaitBackend` 的 `Wait`/`Dispatch` 拆分本就为多后端预留，一行不改即可 |
| 静默截断超过 64 的注册 | 会让「64 上限」这个核心对照点消失。`Register()` 超限明确返回 `kInvalidSlot`，测试断言 70 个只成功 63 个 |
| `bAlertable=FALSE` | 那样 `QueueUserAPC` 回调永远不会执行，APC 实验做不成。用 `TRUE` |
| 用 `std::thread` + `std::condition_variable` 模拟等待 | 目标是学 Windows 系统编程；必须用 `WaitForMultipleObjectsEx` |
| 把 APC 回调直接在 trampoline 里执行 | 破坏 `Wait`(只收集)/`Dispatch`(跑回调) 的 B2 契约。trampoline 只入队，回调交给 `Dispatch()` |

**这个决定让哪件事变得可见：**
1. **IOCP 的价值不是「更快」，是「没有数量上限 + completion 自带上下文」**。WFMO 每个可等待句柄占一个数组槽，硬顶 64；IOCP 一个端口承载任意多完成包。
2. **WFMO 的完成语义更贫瘠**：它只告诉你「第 N 个句柄 signaled」，上层得自己维护 slot→上下文映射；IOCP 的 completion 自带 `lpOverlapped` / `CompletionKey`。这就是为什么 overlapped 操作要走 WFMO 必须给每个 `OVERLAPPED` 配 `hEvent`。
3. **APC 是 Windows 特有的第三种异步投递方式**：只有 `bAlertable=TRUE` 的可警报等待才执行 —— 阶段 1 的 `Waker::Wait` 早就留了 `WaitForSingleObjectEx(..., TRUE)` 这个口子，阶段 5 正面兑现。

## 三、怎么做的（How）

### 3.1 关键数据结构

```cpp
class WfmoBackend final : public IWaitBackend {
    static constexpr size_t kMax = MAXIMUM_WAIT_OBJECTS;  // 64
    static constexpr Slot kInvalidSlot = 0xFFFFFFFF;
    static constexpr size_t kMaxUserHandles = kMax - 1;   // 63（slot 0 给 wake）

    HANDLE handles_[64];            // slot 0 = wake event
    std::function<void()> callbacks_[64];
    bool used_[64];
    std::vector<Slot> signaled_;   // Wait 收集的被触发 slot
    std::vector<ApcItem*> pending_apc_;
    Waker waker_;                  // 复用阶段 1 self-pipe
    HANDLE loop_thread_;           // DuplicateHandle 得到的真实线程句柄（给 QueueUserAPC）
};
```

### 3.2 核心流程 / 调用链

```
[Wait(timeout)]
  把 used_ 的句柄压缩进连续数组（WFMO 要求连续）
  r = WaitForMultipleObjectsEx(n, handles, FALSE, timeout, /*bAlertable=*/TRUE)
    ├─ WAIT_OBJECT_0+i  → signaled_.push_back(slot[i])        → return true
    ├─ WAIT_IO_COMPLETION → APC 已执行（OnApc 已入队）          → return true
    └─ WAIT_TIMEOUT       → 无 I/O 完成（定时器窗口可能到）      → return false

[Dispatch()]（loop 线程）
  signaled_ 里 slot!=0 的 → callbacks_[slot]()   // 用户回调
  pending_apc_ 里        → fn()                  // APC 回调
  清空两个队列

[APC 桥接]
  BindLoopThread()  → DuplicateHandle(GetCurrentThread()) 得真实句柄
  QueueApc(fn)      → new ApcItem{self, fn} → QueueUserAPC(ApcTrampoline, thread, item)
  ApcTrampoline     → self->OnApc(item)：++apc_ran_，item 入 pending_apc_
                       （回调在 loop 线程的可警报等待中执行）
```

`Wake()` = `SetEvent(wake_event_)`，与阶段 1 完全等价；`PostTask` 照旧唤醒 loop。

### 3.3 用到的 Win32 API

| API | 用途 |
|---|---|
| `WaitForMultipleObjectsEx(n, handles, bWaitAll, timeout, bAlertable)` | 对照后端主体；`bAlertable=TRUE` 是 APC 关键 |
| `MAXIMUM_WAIT_OBJECTS` (=64) | 一次等待的句柄硬上限 |
| `WAIT_OBJECT_0` / `WAIT_IO_COMPLETION` / `WAIT_TIMEOUT` | 返回码分流 |
| `QueueUserAPC` / `PAPCFUNC` | 投递 APC；只有可警报等待才执行 |
| `DuplicateHandle(GetCurrentThread())` | 把伪句柄 (-2) 转成可跨线程 `QueueUserAPC` 的真实句柄 |
| `CreateEventW` / `SetEvent` | 注册的测试句柄 + slot 0 唤醒 event |
| `CloseHandle` | 释放复制出的线程句柄 |

### 3.4 遇到的坑与处理（真实发生）

本阶段构建与测试一次通过，没有编译/链接错误。值得记录的两个**设计推演坑**（实现时主动避开）：

| 坑 | 若不处理会怎样 | 处理 |
|---|---|---|
| `QueueUserAPC` 需要真实线程句柄 | `GetCurrentThread()` 是伪句柄 (-2)，跨线程 `QueueUserAPC` 会失败 | `DuplicateHandle` 得到真实句柄，`Shutdown()` 里 `CloseHandle` |
| APC trampoline 只能传 `ULONG_PTR` | 无法直接传 `std::function` | 堆上 `ApcItem*` 作参数，回调里入队，`Dispatch()` 统一执行并 `delete` |
| WFMO 要求句柄数组连续 | `Unregister` 留下空洞会导致数组不连续 | `Wait()` 每次把 `used_` 的句柄压缩进新数组，同时维护 `slot_of_index[]` 反查 |
| 多个 APC 同时到达 | 一次 `WAIT_IO_COMPLETION` 只返回一次 | 所有 APC 的 `OnApc` 都会入 `pending_apc_`，`Dispatch()` 一次跑完（约束 B2 仍成立） |

### 3.5 线程 / 生命周期时序

```
主线程(loop)              任意线程
  │ WfmoBackend 构造（slot0 = wake event）
  │ BindLoopThread() → 真实线程句柄
  │ EventLoop::Run
  │   Dispatch() → tasks/timers/idle
  │   Wait(timeout) ──► WaitForMultipleObjectsEx(alertable=TRUE) 阻塞
  │                       │ SetEvent(wake) ───────────────► WAIT_OBJECT_0
  │                       │ QueueUserAPC ─────────────────► WAIT_IO_COMPLETION
  │   ◄───────────────────┘ （APC trampoline 在 loop 线程入队）
  │   Dispatch() → 用户回调 / APC 回调
  │   ...
  │   loop.Stop() → Run() 退出 → backend_->Shutdown()（关线程句柄/清队列）
```

## 四、后端差异对照表（本阶段的核心产出）

| 维度 | WakerBackend（阶段 1） | WfmoBackend（阶段 5） | IocpBackend（阶段 3，主后端） |
|---|---|---|---|
| 等待 API | `WaitForSingleObjectEx` | `WaitForMultipleObjectsEx` | `GetQueuedCompletionStatusEx` |
| 可等待对象数 | 1 | **最多 64**（`MAXIMUM_WAIT_OBJECTS`），本项目实际 63（slot0 占 1） | **无上限**（一个端口 + 任意多完成包） |
| 完成信息 | 只有「event signaled」 | 「第 N 个句柄 signaled」，需自维护 slot→上下文 | completion 自带 `lpOverlapped` + `CompletionKey` |
| 跨线程唤醒 | `SetEvent` | `SetEvent`（slot 0） | `PostQueuedCompletionStatus(kKeyWake)` |
| 回调执行地点 | loop 线程（TaskQueue） | loop 线程（`Dispatch()`） | loop 线程（`Dispatch()`） |
| 支持 overlapped I/O | 否 | 需给每个 `OVERLAPPED` 配 `hEvent` 才能被等待 | **原生支持**（约束 C7） |
| APC | alertable wait 可触发 | alertable wait 可触发（已实验） | `fAlertable=FALSE`，不走 APC |
| 可扩展性 | 只能靠 `PostTask` | 句柄数到 64 就撞墙 | 加任意多 source 无需改 loop |
| 适用场景 | 纯任务/定时器循环 | 教学对照、少量固定句柄 | 生产级、多源、高吞吐 |

**结论**：同一套 `EventLoop` 接口（阶段 3 的 `IWaitBackend`）能承载三种后端，同一工作负载结果一致（`wfmo=27 iocp=27`）；但只有 IOCP 没有句柄数量上限、且 completion 自带上下文 —— 这就是 Windows 事件循环最终选择 IOCP 的根本原因。

## 六、决策与取舍（偏离约束时必填）

| 约束编号 | 偏离 | 理由 | 是否修订约束文件 |
|---|---|---|---|
| 无 | 无 | 阶段 5 严格遵守 `01-约束.md` B/C/F 各条；`EventLoop`/`IWaitBackend` 零改动 | — |

> **主动补充（非偏离）**：
> 1. `WfmoBackend` 是为教学对照而写的**可用但受限**后端：它不接真实 overlapped I/O 源（阶段 4 的 source 都绑在 `IocpBackend::Handle()`），只做「句柄 signaled → 回调」与 APC 实验。这是刻意的，目的是把差异单独放大，而不是再造一个生产后端。
> 2. `Register()` 复用 `Unregister` 后的空洞槽位；`Wait()` 每次压缩连续数组。
> 3. slot 0 固定给 wake event，因此 `kMaxUserHandles = 63` 而非 64 —— 这个「减 1」本身就是对照点。

## 七、遗留 / 下一阶段衔接

**遗留：**
- `WfmoBackend` 未接入阶段 4 的真实 source（管道/socket/目录）；若要让它们走 WFMO，需给每个 `OVERLAPPED` 配 `hEvent` 并改写 `Watcher::Arm` —— 这会再撞一次「64 上限 + 贫瘠完成语义」，留作可选练习。
- UDP、串口、capstone 串口网络助手尚未实现（阶段 6）。
- 阶段 5 未做性能测试；IOCP 与 WFMO 的吞吐差异不在本阶段学习目标内。
- APC 实验只验证了「能执行」，未验证「非 alertable wait 不执行」的反例（可作为额外练习）。

**下一阶段（阶段 6：Capstone）需要本阶段提供的接口：**
- `IWaitBackend` 抽象 + 注入式 `EventLoop`：capstone 明确选 `IocpBackend`（阶段 5 已证明它没有句柄上限）。
- `EventSource` / `Watcher` close 状态机、`ThreadPool`、`RingBuffer`、`Renderer` 全部就位。
- 阶段 5 的结论（为什么选 IOCP）应写进 capstone 文档的架构理由。

**需要提前注意的坑：**
- 串口 `CreateFile(L"COMx")` 必须带 `FILE_FLAG_OVERLAPPED` 才能关联 IOCP（约束 C7）；`WaitCommEvent` 的 overlapped 用法与 `ReadDirectoryChangesW` 类似，可直接派生 `Watcher`。
- capstone 别再引入第四种后端，保持「一个 IOCP loop + 可插拔 source」的架构收束。
- 优雅关闭仍是 `CloseAll → 取消包 → Reap → Stop`（阶段 4 已验证六源同时关闭）。
