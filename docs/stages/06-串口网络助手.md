## 二、为什么这么做（Why）

### 2.1 为什么串口要 `WaitCommEvent` + `ReadFile` 两段式

TCP 可以「一直挂一个 overlapped recv」，因为 socket 是流式的：有数据就完成，没数据就一直 pending。串口不行 —— 串口是**字符设备**，直接挂 `ReadFile` 时，它的完成时机由 `COMMTIMEOUTS` 决定，而不是「数据到达」。默认超时下 `ReadFile` 会一直等到缓冲区填满或超时，导致「来 1 个字节却收不到」或者「延迟一个超时周期才收到」。

Windows 为此提供了 `WaitCommEvent`：它**只在通信事件发生时完成**（`EV_RXCHAR` = 收到字符）。所以串口的正确形态是两段式：

```
WaitCommEvent(EV_RXCHAR)  →  完成（说明有数据了）  →  ReadFile 取走  →  重新 WaitCommEvent
```

这正是串口和 socket 在**同一个事件循环抽象下**最本质的差异。它没有破坏抽象（两者都是 `EventSource` + `Watcher` + `IoContext`），但确实让 `SerialSource` 内部比 `TcpSource` 多一个状态（`wait_armed_` / `read_in_flight_`）。

**为什么不用「带短超时的 `ReadFile` 轮询」**：那会在没有数据时不断产生「超时完成包」，把事件循环变成忙轮询，违背「无数据时零 CPU」的设计目标。

### 2.2 为什么 `Pump()` 是唯一挂载点

`SerialSource` 里所有「重新开始监听」的动作都收敛到一个 `Pump()`：

```cpp
void SerialSource::Pump() {
    if (state_ != kActive) return;
    if (wait_armed_ || read_in_flight_) return;  // 已有操作在飞，不重复挂
    ArmWait();
}
```

**为什么必须这样**：串口的三个阶段（等事件 → 读 → 再等事件）如果各自都能挂载，就很容易出现「两个 `WaitCommEvent` 同时在飞」—— 同一个 `OVERLAPPED` 被复用两次，内核状态被覆盖，表现是随机的丢数据或崩溃。收敛成单点后，`wait_armed_` / `read_in_flight_` 两个布尔量就足以保证「任意时刻最多一个 `WaitCommEvent` + 一个 `ReadFile`」。

这是阶段 4「全双工必须每个操作独立 `IoContext`」的延续：**ctx 独立**解决「同时有两个操作」，**单点挂载**解决「不会挂出第三个」。

### 2.3 为什么 `CloseAll()` 里要先 `CancelIoEx` 再 `SetCommMask(0)`

这是本阶段**唯一一次真实踩坑并改代码**的地方，也是最有价值的收获。

最初 `SerialSource::CloseAll()` 只做 `PurgeComm` + `EventSource::CloseAll()`（内部 `CancelIoEx`）。测试显示 `WatcherCount()` 永远是 `1` —— watcher 卡在 `kClosing`，`Reap()` 无法回收。

写诊断工具直接观察内核行为，得到确定结论：

| 取消手法 | `GetQueuedCompletionStatus` 结果 |
|---|---|
| `CancelIoEx(h, nullptr)` | `GQCS=0`，`err=995`（`ERROR_OPERATION_ABORTED`）—— **有**完成包 |
| `SetCommMask(h, 0)` | `GQCS=1`，`err=0` —— 完成包以**成功**返回 |
| `PurgeComm(h, ...)` | 超时，**无**完成包 |

`CancelIoEx` 其实会产生完成包（995），那为什么还卡住？进一步诊断发现真正的第二个原因：

**`EventLoop::Run()` 在退出时会调用 `backend_->Shutdown()`，它直接 `CloseHandle(iocp_)` 关闭 IOCP 端口。** 之后任何 `CancelIoEx` 产生的完成包都投递到一个已关闭的端口，`Wait()` 也因 `shutdown_=true` 立即返回 false。于是取消包永远取不出来。

这暴露了一个真实的 API 使用顺序陷阱：

> **`CloseAll()` 必须在事件循环还在运行时调用，不能在 `Run()` 返回之后。**

修正分两处：

1. **测试侧**：不用 `loop.Run()`（它会 Shutdown 后端），改为手动泵 `iocp.Wait()` + `iocp.Dispatch()`。
2. **应用侧**：`serial_net_assistant_main.cpp` 把关闭做成**定时器两段式**，全部在 loop 内完成：
   ```
   t+0    : CloseAll() → CancelIoEx → kClosing
   t+250  : 取消包已排空 → Reap() → Stop()
   ```
   `Run()` 返回时 watcher 已经全部回收，不会再有取消包。

同时给 `SerialSource::CloseAll()` 加上 `SetCommMask(handle_, 0)` 作为**可靠的唤醒手段**（`CancelIoEx` 在部分驱动/时序下不投递完成包，而 `SetCommMask(0)` 实测必定让 `WaitCommEvent` 完成）。顺序必须是先 `EventSource::CloseAll()`（把 watcher 置 `kClosing`）再 `SetCommMask(0)`，否则那个「成功完成包」会被当成正常完成而触发 `Pump()` 重挂。

### 2.4 为什么第一版不做流控、不做 UDP、不做写队列

对照约束 E「第一版只做连上/收/发/显示」：

- **不做硬件流控（RTS/CTS）**：`DCB` 里把 `fRtsControl`/`fDtrControl` 设为 `ENABLE`、关掉 `fOutxCtsFlow`/`fOutxDsrFlow`。流控是「防丢数据」的优化，不影响「能收能发」这个出口条件；加进来会让 `DCB` 配置从 4 个字段膨胀到十几个，淹没本阶段重点。
- **不做 UDP**：阶段 4 已明确推迟。UDP 无连接，没有 accept/close 状态机，加进来不会带来新的 Windows 系统编程知识点。
- **不做写队列**：`Send()` 直接 `WriteFile` 一次，不做排队与背压。串口写通常远快于波特率对应的发送时间，第一版「一次发完」够用；真要做队列，正确形态是「写完成后从队列取下一段」，这是可以独立成阶段的题目。

这些取舍都写进本文件的「决策与取舍」表，避免以后误以为是遗漏。

### 2.5 为什么应用层用 `RingBuffer` 而不是 `std::deque`

日志是典型的「只关心最近 N 条」场景。`std::deque` 无限增长会在长时间运行后吃掉内存；`RingBuffer<std::wstring, 512>` 满了自动丢最旧，并且把 `Dropped()` 暴露到状态栏 —— **背压是可见的**，而不是悄悄丢数据。这与阶段 4 线程池的背压思路一致：宁可丢最旧的显示数据，也不能让内存无界增长或阻塞 loop 线程。

## 三、怎么做的（How）

### 3.1 串口源的三个 `IoContext`

```cpp
class SerialSource::SerialWatcher final : public Watcher {
    IoContext wait_ctx_;   // op_kind = kGeneric → WaitCommEvent
    IoContext read_ctx_;   // op_kind = kRead    → ReadFile
    IoContext write_ctx_;  // op_kind = kWrite   → WriteFile
    DWORD evt_mask_ = 0;   // WaitCommEvent 的输出掩码
};
```

`Watcher::Arm(IoContext&)` 按 `op_kind` 分流（和 `TcpSource::TcpWatcher` 同构）：

```cpp
bool Arm(IoContext& ctx) override {
    ctx.callback = [this, &ctx](uint32_t b, uint32_t e) { OnCompletion(ctx, b, e); };
    switch (ctx.op_kind) {
        case OpKind::kGeneric: {  // WaitCommEvent
            BOOL ok = WaitCommEvent(handle_, &evt_mask_, &ctx.ov);
            return ok || GetLastError() == ERROR_IO_PENDING;
        }
        case OpKind::kRead: {
            ctx.buffer.resize(4096);
            DWORD got = 0;
            BOOL ok = ReadFile(handle_, ctx.buffer.data(), 4096, &got, &ctx.ov);
            return ok || GetLastError() == ERROR_IO_PENDING;
        }
        case OpKind::kWrite: {
            DWORD sent = 0;
            BOOL ok = WriteFile(handle_, ctx.buffer.data(),
                                (DWORD)ctx.buffer.size(), &sent, &ctx.ov);
            return ok || GetLastError() == ERROR_IO_PENDING;
        }
    }
    return false;
}
```

**三个独立 ctx** 是硬要求：`WaitCommEvent` 和 `ReadFile` 会同时在飞（`Pump` 保证最多各一个），共用一个 `OVERLAPPED` 会互相覆盖。

### 3.2 打开串口的完整流程

```cpp
bool SerialSource::Start() {
    std::wstring path = DevicePath(cfg_.port);   // "COM2" → "\\\\.\\COM2"
    handle_ = CreateFileW(path.c_str(), GENERIC_READ | GENERIC_WRITE,
                          0, nullptr, OPEN_EXISTING,
                          FILE_ATTRIBUTE_NORMAL | FILE_FLAG_OVERLAPPED, nullptr);
    if (handle_ == INVALID_HANDLE_VALUE) { last_comm_error_ = GetLastError(); return false; }

    DCB dcb{}; dcb.DCBlength = sizeof(DCB);
    if (!GetCommState(handle_, &dcb)) { /* 失败清理 */ }
    dcb.BaudRate = cfg_.baud;
    dcb.ByteSize = cfg_.byte_size;   // 8
    dcb.Parity   = cfg_.parity;      // NOPARITY
    dcb.StopBits = cfg_.stop_bits;   // ONESTOPBIT
    dcb.fBinary  = TRUE;
    dcb.fParity  = FALSE;
    dcb.fOutxCtsFlow = FALSE; dcb.fOutxDsrFlow = FALSE;  // 无流控
    dcb.fDtrControl  = DTR_CONTROL_ENABLE;
    dcb.fRtsControl  = RTS_CONTROL_ENABLE;
    if (!SetCommState(handle_, &dcb)) { /* 失败清理 */ }

    // 关键：ReadIntervalTimeout = MAXDWORD 表示「有字节就立即返回，不等间隔」
    COMMTIMEOUTS to{};
    to.ReadIntervalTimeout = MAXDWORD;
    to.ReadTotalTimeoutMultiplier = 0;
    to.ReadTotalTimeoutConstant = 0;
    SetCommTimeouts(handle_, &to);

    SetCommMask(handle_, EV_RXCHAR);            // 只关心「收到字符」
    iocp_.Associate(handle_, kKeyWatcher);      // 挂到同一个 IOCP
    // ... 建立 watcher，接好三个 on_complete，最后 Pump()
}
```

`\\\\.\\` 前缀不能省：`"COM10"` 及以上不加前缀会被当成文件名，`"COM2"` 虽能工作但为一致性统一加。

### 3.3 三个完成回调的分工

```cpp
// 读完成：交付数据 → 重新挂 WaitCommEvent
read_ctx_.on_complete = [this](IoContext& ctx, uint32_t bytes, uint32_t error) -> bool {
    if (error == 0 && bytes > 0) {
        ++read_ops_; recv_bytes_ += bytes;
        std::vector<uint8_t> chunk(ctx.buffer.begin(), ctx.buffer.begin() + bytes);
        if (cb_) cb_(chunk);        // 已在 loop 线程
    } else if (error != 0) {
        last_comm_error_ = error;
    }
    Pump();
    return true;                    // 已自行处理，Watcher 不再 auto_rearm
};

// WaitCommEvent 完成：有字符 → 发起 ReadFile
wait_ctx_.on_complete = [this](IoContext& ctx, uint32_t bytes, uint32_t error) -> bool {
    wait_armed_ = false;
    if (error != 0) { last_comm_error_ = error; return true; }
    ++wait_events_;
    if ((evt_mask_ & EV_RXCHAR) && !read_in_flight_) ArmRead();
    else Pump();
    return true;
};

// 写完成：只累计字节
write_ctx_.on_complete = [this](IoContext& ctx, uint32_t bytes, uint32_t error) -> bool {
    if (error == 0) sent_bytes_ += bytes;
    return true;
};
```

全部返回 `true`，表示「source 自己接管了后续挂载」，`Watcher` 的 `auto_rearm` 分支不会介入。这是阶段 4 引入的 `on_complete` 钩子契约。

### 3.4 应用的优雅关闭（定时器两段式）

```cpp
auto begin_shutdown = [&]() {
    loop.PostTask([&]() {
        serial.CloseAll();     // CancelIoEx + SetCommMask(0) → kClosing
        tcp.CloseAll();
        app.Draw();
        loop.PostDelayedTask(250, [&]() {   // 给取消完成包留出排空时间
            serial.Reap();                  // 只删 kClosed
            tcp.Reap();
            app.Draw();
            renderer.RenderTick();
            loop.Stop();
        });
    });
};
```

`250ms` 是保守值：取消完成包通常在毫秒内到达，250ms 足够覆盖调度抖动。这比「在 `Run()` 返回后自己再泵」可靠得多 —— 后者根本拿不到包（后端已 Shutdown）。

### 3.5 双源共享一个循环

```cpp
core::EventLoop loop(clock, std::make_unique<io::IocpBackend>());

io::SerialSource serial(iocp, cfg, [&](auto& d) { app.OnSerialData(d); });
io::TcpSource    tcp(iocp,        [&](auto& d) { app.OnNetworkData(d); });

serial.Start();   // 串口句柄 Associate 到同一个 IOCP
tcp.Start();      // socket 也 Associate 到同一个 IOCP
loop.Run();       // 一个线程，一个等待点
```

两个完全不同类型的设备（字符设备 + 流式 socket）在同一个 `GetQueuedCompletionStatusEx` 上等待，靠 `IoContext::owner` 区分归属。这就是 IOCP 相对 `WaitForMultipleObjects` 的核心优势 —— 阶段 5 已用 63 句柄上限做过对照。

### 3.6 验证方式

| 验证项 | 方法 | 结果 |
|---|---|---|
| 打开不存在的串口 | `COM99` → 期望 `Start()` 返回 false 且 `LastCommError() != 0` | 通过 |
| 真实串口完整生命周期 | COM1：打开→DCB→超时→掩码→Associate→`WaitCommEvent`→`CloseAll`→`Reap` | watcher 归零 |
| 串口数据回环 | COM2↔COM3（com0com 虚拟对） | **跳过**，见下 |
| TCP 双向 | `PeerSocket()` 注入 7 字节 + `Send` 3 字节读回 | 通过 |
| 双源同 loop 干净退出 | 同时 `CloseAll` → 排空 → `Reap` | tcp=0 serial=0 |
| 应用逻辑 | 收/发/背压/目标切换/ESC 退出 | 12 项全通过 |
| 真实控制台 | `--run-ms 1200` 自动优雅关闭 | 无泄漏 |

**关于串口回环被跳过（诚实记录）**：本机 `COM2` = `\Device\VSerial_0`、`COM3` = `\Device\VSerial_1`（com0com 虚拟对），但当前进程**未提权**（`Admin=False`），以任何共享模式打开这两个端口都返回 `ERROR_ACCESS_DENIED`（err=5），而真实串口 `COM1` 可以正常打开。因此「写入一端、从另一端读回」的端到端数据验证无法在此环境完成，测试**明确跳过而不是虚报成功**。串口的 I/O 路径本身已由 COM1 生命周期测试覆盖（`WaitCommEvent` 真实挂起并被 `SetCommMask(0)` 唤醒）。

## 四、决策与取舍（Decisions）

| # | 决策 | 理由 | 代价 / 后续 |
|---|---|---|---|
| S6-1 | 串口用 `WaitCommEvent` + `ReadFile` 两段式，不用裸 `ReadFile` | 串口是字符设备，`ReadFile` 完成时机由 `COMMTIMEOUTS` 决定而非「数据到达」；裸读会漏数据或引入超时延迟 | 比 TCP 多两个状态标志（`wait_armed_`/`read_in_flight_`） |
| S6-2 | `Pump()` 作为唯一挂载点 | 防止两个 `WaitCommEvent` 同时在飞复用同一 `OVERLAPPED` | 需要保证所有路径都经过 `Pump()` |
| S6-3 | `CloseAll()` 先 `EventSource::CloseAll()` 再 `SetCommMask(0)` | `CancelIoEx` 在部分驱动下不投递完成包；`SetCommMask(0)` 实测必定唤醒。顺序反了会让成功完成包触发重挂 | 串口特有，无法泛化到其他 source |
| S6-4 | 关闭走「定时器两段式」，全部在 loop 内完成 | `EventLoop::Run()` 返回时后端已 `Shutdown()`（IOCP 句柄已关），之后再 `CancelIoEx` 的完成包永远取不到 | 需要 250ms 排空窗口 |
| S6-5 | 第一版无硬件流控（8N1、DTR/RTS 常开） | 流控只影响「防丢数据」，不影响「能收能发」出口条件 | 高速/长线场景需补 RTS/CTS |
| S6-6 | 第一版不做写队列，`Send()` 直接 `WriteFile` | 串口写通常快于波特率发送时间，一次发完够用 | 高频小包场景需「写完成→取下一段」队列 |
| S6-7 | 不做 UDP（沿用阶段 4 推迟） | 无连接、无 accept/close 状态机，不带来新的系统编程知识点 | 后续可作独立阶段 |
| S6-8 | 日志用 `RingBuffer<wstring, 512>`，`Dropped()` 上状态栏 | 背压可见、内存有界、不阻塞 loop | 旧日志丢失（符合「只关心最近」语义） |
| S6-9 | 输入行上限 240 字符 | 防止无界增长 | 超长粘贴会被截断 |
| S6-10 | 只用 ASCII 交互（约束 D7） | 避开 IME 与宽字符宽度计算 | 中文输入需独立阶段 |
| S6-11 | 提供 `--selftest` / `--run-ms` 两种无交互模式 | 让 CI 与自动化能验证完整链路，不必人工按键 | 多两个参数分支 |

## 五、踩过的坑（Lessons）

1. **`EventLoop::Run()` 返回后不能再做 I/O 收尾**。`Run()` 末尾调用 `backend_->Shutdown()` 关闭 IOCP 句柄，之后的 `CancelIoEx` 完成包投递到已关闭端口，`Wait()` 也因 `shutdown_=true` 立即返回 false。现象是 `WatcherCount()` 永远停在 1。修法：所有关闭动作放进 loop 内的定时器。这是本项目最值得记住的一条 API 顺序约束。

2. **`CancelIoEx` 对串口 `WaitCommEvent` 的完成包投递不可靠**。诊断实测 `GQCS=0 err=995`（说明有包），但在其他时序下可能不投递。可靠手法是 `SetCommMask(h, 0)`，实测必定以成功完成包返回。

3. **`PurgeComm` 不能用来取消 `WaitCommEvent`**。诊断实测超时无完成包。它只用于丢弃缓冲区数据。

4. **`RunOneIterationForTest()` 只做 `Dispatch()` 不做 `Wait()`**。取消完成包必须先由 `Wait()` 从内核取出才能被 `Dispatch()`，所以测试里驱动关闭流程必须显式 `Wait → Dispatch → Reap`。

5. **`\\\\.\\` 前缀**：`COM10` 及以上不加前缀会被当成文件名。

6. **`ReadIntervalTimeout = MAXDWORD`** 是「有字节立即返回」的语义，配合 `ReadTotalTimeout* = 0` 才是非阻塞语义；设错会让 `ReadFile` 一直等。
